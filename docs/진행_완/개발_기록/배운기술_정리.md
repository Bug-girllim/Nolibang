## 1. 개발 환경 / 빌드 도구

| 항목 | 예제에서 사용한 것 | 설명 |
|---|---|---|
| JDK | **Java 21** (temurin-21) | 모든 Gradle 프로젝트가 `languageVersion = JavaLanguageVersion.of(21)` |
| IDE | IntelliJ | Java 기초(03)는 Gradle 없는 IntelliJ 모듈 프로젝트 |
| 빌드 | **Gradle** (Groovy `build.gradle`) | `plugins`, `repositories { mavenCentral() }`, `dependencies` 구성 |
| Spring Boot | 4.1.2 (MVC, JPA chap01~03) / **3.5.13** (JPA 미니 프로젝트, Security) | `io.spring.dependency-management 1.1.7` 함께 사용 |
| 순수 Spring | `spring-context 7.0.8`, `spring-aop 7.0.8`, `aspectjweaver 1.9.25.1` | Spring Core 과목(Boot 없이 사용) |
| DB 드라이버 | `com.mysql:mysql-connector-j` (JDBC 과목은 8.4.0) | MySQL 연결 |
| 테스트 | JUnit 5 (`junit-jupiter`) | 의존성만 있고 실제 테스트 코드는 거의 없음 |
| 개발 편의 | `spring-boot-devtools` | 코드 변경 시 자동 재시작 |

developmentOnly 'org.springframework.boot:spring-boot-devtools'

## 3. MySQL (04_MySQL)

> 실습 DB가 **`wanted_lms`** (users, courses, enrollments, grades, user_auth_providers 테이블)로, 우리 LMS 프로젝트와 도메인이 거의 같다. 메뉴 예제는 `menudb`(tbl_menu, tbl_category)를 사용한다.

| 파일 | 기술 | 설명 |
|---|---|---|
| 01_select | `SELECT`, `*`, `AS`(별칭), `now()`, `concat()` | 원하는 컬럼 조회 |
| 02_orderby | `ORDER BY ... ASC/DESC`, `IS NULL` 정렬 | 결과 정렬 |
| 03_where | `WHERE`, 비교 연산자, `AND/OR`, `LIKE`, `IN`, `BETWEEN`, `NOT` | 조회할 행 조건 |
| 04_distinct | `DISTINCT` | 중복 제거 |
| 05_limit | `LIMIT offset, count` | **페이징 구현의 기본** |
| 06_grouping | `COUNT/SUM/AVG/MAX/MIN`, `GROUP BY`, `HAVING` | 통계 (예: 교육자별 개설 강좌 수) |
| 07_Join | `INNER JOIN`, `LEFT/RIGHT JOIN`, FK 개념 | courses ↔ users(교육자 이름) 조인 |
| 08_subqueries | WHERE절 서브쿼리, FROM절 서브쿼리(인라인 뷰) | 복합 조건 조회 |
| 09_ddl | `CREATE TABLE`, 데이터 타입(INT, VARCHAR, TEXT, DATE, DATETIME, TIMESTAMP), 제약조건(`PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `DEFAULT`, `FOREIGN KEY ... REFERENCES`), `COMMENT`, `ALTER TABLE ADD/MODIFY/DROP COLUMN`, `DROP` vs `TRUNCATE` | 테이블 설계 |
| 10_dml | `INSERT`, `UPDATE`, `DELETE`, 제약조건 위반 사례(UNIQUE, NOT NULL, FK 참조 무결성) | 데이터 조작. **UPDATE/DELETE는 반드시 PK로 WHERE** |
| 11_union | `UNION` | 쿼리 결과 합치기 |

| 14_transactional | `START TRANSACTION`, `COMMIT`, `ROLLBACK` | 계좌이체 예제. 여러 작업을 하나의 단위로 처리 |

## 4. JDBC (05_JDBC)

Java 코드로 MySQL에 직접 접속하는 방법. JPA가 내부적으로 해주는 일을 이해하는 단계.

| 기술 | 설명 | 예제 위치 |
|---|---|---|
| `DriverManager.getConnection()` | `Class.forName("com.mysql.cj.jdbc.Driver")` 후 URL/계정으로 `Connection` 생성 | `chap01/a_connection/Application01` |
| `Properties` 설정 분리 | DB 접속 정보를 `jdbc-config.properties`로 분리해 코드에 노출하지 않음 | `Application02` |
| `JDBCTemplate` | `getConnection()`, `close()`를 static 메서드로 묶어 중복 제거 | `chap01/b_template` |
| `Statement` + `ResultSet` | `executeQuery()`로 조회, `rset.next()`로 한 행씩 읽기 | `chap02/a_statements` |
| **`PreparedStatement`** | `?` 플레이스홀더 + `setString/setInt`. SQL 재사용 성능 향상, **SQL Injection 방지** | `chap02/b_preparedstatements` |
| ResultSet → DTO | 조회 결과를 `MenuDTO` 객체에 옮겨 담기 | `Application03` |
| SQL을 XML로 분리 | `Properties.loadFromXML()` + `<entry key="...">` | `menu-query.xml`, `queries.xml` |
| `executeUpdate()` | INSERT/UPDATE/DELETE, 반환값 = 영향 받은 행 수 | `Application04` |
| **try-with-resources** | `try (Connection con = ...)` 자원 자동 해제 | `chap03-crud/MenuService` |
| static 초기화 블록 | 클래스 로드 시 1번만 설정 파일 읽기, `getClassLoader().getResourceAsStream()` | `QueryUtil`, `JDBCTemplate` |
| **계층 구조 (MVC)** | View → Controller → Service → DAO → DB, 각 계층의 해야 할 일 / 하면 안 되는 일을 주석으로 정리 | `chap03-crud/restaurant` |

## 5. Servlet (06_Servlet)

Spring MVC가 내부적으로 쓰는 기반 기술. (Jakarta Servlet 6.1, `war` 플러그인)

| 기술 | 설명 | 예제 위치 |
|---|---|---|
| `@WebServlet("/경로")` + `HttpServlet` | URL과 서블릿 클래스 연결 | `a_lifecycle` |
| 생명주기 | 생성자 → `init()` → `service()` (요청마다) → `destroy()` | `LifeCycleServlet` |
| `doGet` / `doPost` | HTTP 메서드별 처리. GET = URL 노출·빠름·조회용, POST = Body 전송·대용량·등록용 | `b_service`, `c_parameter` |
| 파라미터 받기 | `req.getParameter("name")` → 항상 String, 필요 시 `Integer.parseInt` | `c_parameter` |
| 응답 | `resp.getWriter()`로 HTML 직접 출력 | `d_response` |
| 에러 처리 | `resp.sendError(404, ...)`, `web.xml`의 `<error-page>` | `e_exception` |

| **Filter** | 서블릿 도착 전에 실행. `@WebFilter` 또는 `web.xml` 등록. 인코딩 필터, 로그인 확인 필터, 수행 시간 측정 필터 | `i_filter` |

## 6. Spring Core – IoC / DI / AOP (07_Spring-Core)

결제(KakaoPay/NaverPay) 예제와 회원 관리 예제로 진행.

### 6-1. IoC 컨테이너 (chap01)

| 기술 | 설명 |
|---|---|
| 문제 인식 | `new KakaoPayGateway()`처럼 직접 생성하면 결합도가 높아 **OCP(개방-폐쇄 원칙)** 위반 |
| 인터페이스로 해결 | `PaymentInterface`를 만들고 구현체를 교체 가능하게 |
| `@Configuration` + `@Bean` | 설정 클래스에서 Bean(Spring이 관리하는 객체) 등록. 이름 기본값 = 메서드명 |
| `ApplicationContext` | `new AnnotationConfigApplicationContext(AppConfig.class)`, `getBean("이름", 타입)` |
| Bean Scope | 기본 **singleton**(하나를 공유), `@Scope("prototype")`(요청마다 새로 생성) |
| ⚠ 주의 | 싱글톤 Bean(Service, DAO)에 **상태 필드를 두지 말 것** → 모든 요청이 공유됨. 데이터는 DTO로 전달 |

### 6-2. DI 의존성 주입 (chap02)

| 기술 | 설명 |
|---|---|
| `@ComponentScan(basePackages=...)` | 지정 패키지의 `@Component` 계열 클래스를 자동 Bean 등록. `excludeFilters`로 제외 가능 |
| `@Component`, `@Service` | Bean 등록 어노테이션 (`@Service`는 Service 계층용 `@Component`) |
| `@Autowired` | 컨테이너에서 Bean을 찾아 주입 |
| 필드 주입 | 간단하지만 `final` 불가 |
| setter 주입 | 선택적 의존관계 가능, 호출 안 되면 null |
| **생성자 주입 (권장)** | `final`로 불변성 보장, 필수 의존성 강제. 생성자가 1개면 `@Autowired` 생략 가능 → 실제로는 Lombok `@RequiredArgsConstructor`로 작성 |

### 6-3. AOP (chap03)

| 기술 | 설명 |
|---|---|
| 문제 인식 | 모든 메서드에 로깅·성능측정 코드가 반복(중복, 낮은 응집도, 유지보수 어려움) |
| `@EnableAspectJAutoProxy` | AOP 활성화 (Boot에서는 자동) |
| `@Aspect` + `@Component` | 공통 기능(관점)을 모아둔 클래스 |
| Pointcut 표현식 | `execution(* com.wanted.aop.section02.MemberService.*(..))` |
| Advice | `@Before`, `@After`, `@AfterReturning(returning="result")`, `@AfterThrowing`, **`@Around`**(`ProceedingJoinPoint.proceed()`로 앞뒤 모두 처리) |
| `JoinPoint` | 실행 중인 메서드 이름(`getSignature().getName()`), 매개변수(`getArgs()`) |
| `@Order(1)` | 여러 Aspect의 실행 순서 |

## 7. Spring Web MVC (08_Spring-Web-MVC)

Spring Boot + 내장 Tomcat. `@Controller`가 요청을 받아 처리한다.

| 기술 | 설명 | 예제 위치 |
|---|---|---|
| `@SpringBootApplication` | 실행 클래스. 자신의 패키지 하위만 스캔 | 각 chap의 Application |
| `application.yaml` | `server.port`, `spring.application.name`, multipart 설정, 사용자 정의 값(`file.upload-dir`) | 각 chap |
| `@Controller` + `@RequestMapping` | 클래스/메서드에 URL 매핑 (`method = RequestMethod.POST`) | `chap01-request-mapping` |
| `@GetMapping` / `@PostMapping` | HTTP 메서드별 매핑 | `chap01` |
| **`@PathVariable`** | `/order/detail/{orderNo}` URL 경로의 값 받기 | `ClassController` |
| `WebRequest` | `request.getParameter()`로 값 받기 | `chap02/RequestController` |
| **`@RequestParam`** | 쿼리스트링/폼 값 받기. name이 다르면 400 에러 | `chap02` |
| **`@ModelAttribute`** | 여러 입력값을 DTO 하나로 바인딩 | `chap02` |
| `Model` / `ModelAndView` | 응답에 데이터 담기, `setViewName()` | `chap03-view-resolver` |
| View 반환 3가지 | `void`(URL=뷰 경로), `String`(뷰 이름), `ModelAndView` | `ResolverController` |
| **`redirect:`** + `RedirectAttributes` | `return "redirect:/"`, `addFlashAttribute()`로 리다이렉트 후에도 1회 값 유지 | `ResolverController` |
| `@ExceptionHandler` | 컨트롤러 안 예외 처리 | `chap04/ExceptionTestController` |
| **`@ControllerAdvice`** | 전역 예외 처리 클래스. 우선순위: 같은 클래스 핸들러 > 전역 핸들러 | `chap04/GlobalExceptionHandler` |
| **Interceptor** | `HandlerInterceptor`의 `preHandle`/`postHandle` (수행 시간 측정) | `chap05/TimerInterceptor` |
| `WebMvcConfigurer` | `addInterceptors()`(경로 포함/제외), `addResourceHandlers()`(업로드 폴더를 URL로 노출) | `chap05`, `chap06/WebConfig` |

### 8-2. Spring Data JPA (module07 미니 프로젝트)

| 기술 | 설명 |
|---|---|
| **`JpaRepository<엔티티, PK타입>`** | interface만 만들면 `save`, `findById`, `findAll`, `delete` 등 자동 제공 |

## 11. 수업에서 사용한 설계 규칙 (미니 프로젝트 기준)

팀 프로젝트에서 그대로 따라 하면 되는 규칙들이다.

**패키지 구조 (도메인별)**

```
com.wanted.project
├── domain
│   └── menu
│       ├── controller      MenuController
│       └── model
│           ├── dao         MenuRepository (JpaRepository)
│           ├── dto         MenuDTO (from() 변환, @Valid 검증 규칙)
│           ├── entity      Menu (도메인 규칙, setter 없음)
│           ├── policy      MenuNamePolicy 등 (조회가 필요한 비즈니스 규칙)
│           └── service     MenuService (흐름 + @Transactional)
└── global
    ├── config              Application, ContextConfig, JpaConfig
    └── exception           BusinessException, ErrorCode, GlobalExceptionHandler
```

**계층별 책임**

| 계층 | 해야 할 일 | 하면 안 되는 일 |
|---|---|---|
| Controller | 요청 받기, `@Valid` 선언, 응답 결정 | 비즈니스 로직, 트랜잭션, Entity 다루기, try-catch |
| Service | 흐름 조립(조회 → 규칙 확인 → 변경 → 저장 → DTO 변환), `@Transactional` | 규칙을 if문으로 직접 판단, Entity를 밖으로 반환 |
| Entity | 자기 상태로 판단하는 **도메인 규칙** (`stopSelling()`, `validateDeletable()`), 정적 팩토리 `create()` | setter 공개, Repository 주입, DTO 알기 |
| Policy | DB 조회가 필요한 **비즈니스 규칙** (이름 중복 등). 위반 시 예외만 던짐 | 저장·상태 변경 |
| DTO | 입력 형식 검증, `from(Entity)` 변환 | DB 접근, 비즈니스 로직 |
| Repository | 조회/저장 선언 | DTO 변환, 규칙 판단 |

**Entity ↔ DTO 변환**: Entity → DTO는 `DTO.from(entity)`, DTO → Entity는 `Entity.create(값...)` (ModelMapper 사용 안 함)

**팀 간 협업 규칙 (4인 팀 분업에 바로 적용 가능)**

1. 다른 팀의 Repository/Entity를 import하지 않는다. 합의한 **인터페이스**로만 묻는다.
2. 값은 Entity가 아닌 기본형/DTO로 주고받는다.
3. 필요한 쪽이 인터페이스를 정의하고, 정보를 가진 쪽이 구현한다. (순환 의존 방지)
4. 상대 구현이 없으면 **Fake 구현체**로 먼저 개발한다. (`FakeMenuOrderHistoryChecker`)
5. 계약을 바꿔야 하면 상대 팀과 합의한 뒤 바꾼다.

### 12-2. 프론트 없이 백엔드만 할 때 주의할 점

수업 예제는 대부분 **`@Controller` + Thymeleaf 화면(View 반환)** 방식이다. 프론트를 쓰지 않는다면 **데이터(JSON)를 반환하는 방식**으로 만들어야 한다.

- 수업에서 다룬 방법: 메서드에 **`@ResponseBody`** 를 붙이면 객체가 JSON으로 반환된다. (미니 프로젝트 `/menu/category`, Security `/method/*`)
- 백엔드 전용이면 모든 메서드에 `@ResponseBody`를 붙이거나, 같은 효과를 클래스 전체에 주는 `@RestController`(= `@Controller` + `@ResponseBody`)를 쓰는 것이 일반적이다.
- ⚠ 아래는 **수업 예제에 나오지 않은 기술**이다. 쓰려면 팀에서 따로 학습해야 한다.
  - `@RestController`, `@RequestBody`(JSON 요청 본문 받기), `ResponseEntity`(상태코드 지정 응답), `@RestControllerAdvice`
  - `Pageable` / `Page`(Spring Data 페이징), `@OneToMany` 양방향 연관관계
  - JWT 토큰 인증 (수업은 **세션 방식**만 다룸)
- 화면이 없으므로 API 테스트는 Postman 같은 도구나 IntelliJ HTTP Client로 한다. (수업 자료에는 없음)
- `redirect:` 반환, `ModelAndView`, `RedirectAttributes`, 에러 화면(`error/error`)은 화면 전용 방식이므로 JSON 응답 방식으로 바꿔야 한다.
- Security의 `formLogin`과 성공/실패 핸들러의 페이지 이동도 화면 기준이다. 백엔드만 할 경우 핸들러에서 페이지 이동 대신 JSON 응답을 내려주도록 바꾸는 방안을 팀에서 정해야 한다.
