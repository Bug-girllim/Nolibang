### 후속 조치 필요

**[10번] 관리자가 강사를 비활성화해도 이미 로그인한 세션은 계속 쓸 수 있다.**
- 재현: teacherA 로그인 → 관리자가 `POST /admin/instructors/6/status active=false` → teacherA의 기존 세션으로 `GET /instructor` 가 계속 200. 새 로그인은 `?error=disabled`로 차단.
- 원인: `AuthDetails.isEnabled()`가 로그인 시점에만 검사되고, 세션에 든 사용자 정보를 요청마다 DB 상태와 대조하지 않는다. 활동이 있으면 세션 유지 시간도 계속 연장된다.
- 제안: `InstructorAccountService.changeStatus`에서 비활성화할 때 해당 사용자의 세션을 만료(`SessionRegistry.expireNow`). `HttpSessionEventPublisher`는 이미 등록돼 있다.
- 탈퇴 계정은 같은 구조이지만 탈퇴를 본인만 하고 `maximumSessions(1)`이 있어 남는 세션이 없다.

**[4·5번] 체크리스트와 팀 결정(11-06)이 충돌한다.**
- 선택지: (a) 체크리스트에서 두 항목을 뺀다, (b) 약관·만 14세 동의를 다시 넣는다. 법적으로 만 14세 미만 가입이 문제가 되는 서비스라면 (b) 검토 필요.
- 참고: `docs/기획/07-screens.md`에는 강사 약관 확인(C-08)이 남아 있어 11-06 결정과 어긋난다.

**[참고] 메일 서버가 없으면 가입이 500 오류로 끝난다.**
- 메일 발송 실패 시 가입은 롤백(DB에 흔적 없음)되지만 사용자에게는 "일시적인 오류" 화면만 보인다. 안내 문구를 따로 두면 좋다.

### 점검 방법·한계
- 코드: `SignupDTO`, `SignupController`, `UserService`, `AuthDetails`, `AuthService`, `SecurityConfig`, `AccountController`, `WithdrawalService`
- 테스트: `UserServiceTest`·`EmailVerificationServiceTest`·`AccountRecoveryAndSettingsTest`는 메일을 받을 수 있어야 통과한다. 메일 비밀번호가 없는 환경에서는 8개가 `MailAuthenticationException`으로 실패하므로, 로컬 가짜 SMTP를 붙여 전부 통과를 확인했다. `UserWithdrawTest` 4개, `SecurityConfigTest` 87개도 통과.
- 실제 서버: 포트 8081, DB `wanted_lms`(시드 초기화), 학습자·강사·관리자 계정으로 curl 시나리오 실행.
- 확인 못 한 것: 실제 Gmail 발송, 60분 세션 만료 실제 대기.

## ② 카테고리·취미·강의 관리

기준 커밋 `de0c5fc` (main) · 점검일 2026-11-10

### 구조 (점검 전제)
- 대분류·세부 취미의 노출 상태는 3가지다: **운영 중(OPERATING) / 준비 중(PREPARING) / 비공개(PRIVATE)**. 체크리스트의 "미운영"에 해당하는 값은 없고, "숨김"은 비공개다.
- 강의(`courses.status`)는 **OPEN / CLOSED** 두 가지뿐이다. 강의 단위의 "준비 중"은 없고, 준비 중은 취미·대분류 단위로만 있다. 공예(준비 중) 아래에는 강의가 아예 없다.
- 개인 제작 강의는 기획에서 [확장 D-45]로 분류돼 MVP에 없다. 강의 등록·삭제 기능도 없다(D-59: 강의는 시드 데이터).

### 후속 조치 필요

**[9번] 강의를 CLOSED(비공개)로 바꾸면 수강 중인 학습자가 차시 화면을 열 수 없다.**
- 재현: 관리자가 `색연필화 응용`(강의 2)을 CLOSED로 저장 → 수강 중인 learner의 `GET /lessons/6?enrollmentId=2`가 404. 같은 시점에 `/videos/6`은 206, `/assignments`는 200, 내 학습 현황은 정상.
- 원인: `CourseService.getCourseDetailForEnrolled`가 `isVisible(found, Role.USER)`로 거른다. 코드 주석에 "닫힌(CLOSED) 강의는 기존처럼 찾지 못한다"고 적혀 있다. 반면 같은 클래스의 `updateCourse` 주석은 "이미 수강 중인 학습자의 학습은 그대로"라고 적혀 있어 서로 모순이다. 취미 준비 중에 대해서는 테스트가 있지만, 강의 CLOSED + 수강 중 학습자 테스트는 없다.
- 기획 근거: D-42(영상 접근은 수강 30일 이내 또는 수료자)와 D-20. 수료자의 무제한 재시청도 같은 경로라 CLOSED 강의에서는 막힐 가능성이 높다(직접 확인하지는 않음).
- 제안: 수강 중·수료한 학습자에게는 CLOSED 필터를 적용하지 않도록 고치고, 그 경우를 `PreparingHobbyEnrolledAccessTest`와 같은 방식으로 테스트에 추가. 의도된 동작이라면 영상·과제도 같이 막도록 정책을 한쪽으로 맞춰야 한다.

**[3번] 준비 중 취미 열람이 grant와 무관하다.**
- 의도(강사 전체 공개)인지 확인이 필요하다. 의도가 아니라면 `HobbyService.isVisible`에서 강사는 `hasHobbyGrant`를 확인해야 한다. 시드에도 준비 중 취미(4~7)에 대한 grant가 없어, 현재 데이터로는 "허용된 강사"를 구분해서 볼 수 없다.

**[7번·기획] 운영 중 전환 조건이 강제되지 않는다.**

### 후속 조치
- **[7번] 최종 과제 제출 실패 시 고아 파일**: `AssignmentService.saveNewRound`가 DB 쓰기 이후 예외가 나면 저장한 이미지를 지우도록 하거나, 파일 삭제를 트랜잭션 롤백 시점(`TransactionSynchronization.afterCompletion`)에 연결해야 한다. 같은 방식으로 `edit`의 이전 파일 삭제도 커밋 이후(`afterCommit`)로 옮기는 것이 안전하다.
- **[⑤에도 해당 — 새로 발견] 담당 강사가 없는 분반의 수강생은 최종 과제를 제출할 수 없다.** 제출은 담당 강사에게 알림을 보내야 하는데 담당이 없으면 `notify(null)`이 `입력값을 확인해 주세요.`를 던져 제출이 통째로 롤백된다. 기획(`05-policy.md` Q-05 "담당 공백 분반의 기존 수강자도 영상 진도·30일 내 과제 제출은 계속 가능하나 자동 수료되지 않는다")과 어긋난다. 수정은 알림 대상이 없으면 알림만 건너뛰는 것이다(`ReviewRound` 저장과 파일 저장은 그대로). ⑤번 점검에서는 이 경우를 확인하지 못했다.
- **[10번] 탈퇴 시 작품·이미지 삭제**: 기획의 확정 원칙(수강/진도·수료/배지·복습/강사 피드백·본인 최종 과제/일반 작품·이미지/공개 게시물 삭제)을 `WithdrawalService`가 아직 이행하지 않는다. 기획 대비 차이를 짚을 때 언급한 "탈퇴 시 학습 데이터 삭제 미이행"과 같은 문제다. 삭제 시에는 DB 행과 함께 디스크(또는 S3)의 파일도 지워야 한다.
- **[3번] 실제 이미지 여부 검증**: 지금은 12바이트 매직 바이트만 본다. 저장 전에 `ImageIO` 등으로 한 번 읽어 보거나(WebP는 별도 처리), 최소한 PNG/JPEG의 끝 표식까지 확인하면 "머리만 이미지인 파일"을 막을 수 있다. 우선순위는 낮다(`nosniff`와 저장 MIME으로 실행 위험은 이미 낮다).
- **[5번] 큰 요청 거부 시 안내**: 500MB 초과·한글 300자 파일명은 413으로 거부되지만 사용자에게 보이는 안내는 확인하지 못했다.
