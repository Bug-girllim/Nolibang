## 0. Claude Code 작업 지시

### 0-1. 프로젝트
- `lms-practice` — Spring Boot 4.1.2 · Java 21 · Thymeleaf · Spring Security(formLogin) · JPA · MySQL(DB 이름 `nolibang`, utf8mb4, UTC)
- 패키지 `com.wanted.lmspractice`
- 스키마·시드: `src/main/resources/sql/schema.sql`, `src/main/resources/sql/seed.sql`
- 참고 문서(있으면): 상위 폴더의 `기획/03-requirements.md`, `API_명세서.md`, `데이터베이스/DB_설계서.md`, `패키지_구조_설계.md`

### 0-2. 지켜야 할 것
1. **소스 코드·템플릿·설정 파일을 고치지 않는다.** 이번 작업은 검증이다. 문제가 있으면 결과 파일에 보고만 한다.
2. 기대 결과는 아래 표에 적힌 것만 기준으로 삼는다. 표·참고 문서에 없는 기준을 만들지 않는다. 판단할 수 없으면 ❓로 적는다.
3. 로컬 DB는 바꿔도 된다(시각 변경 UPDATE 등). 상태를 바꾸는 항목을 확인한 뒤에는 DB를 다시 적재한다.
4. 앱 실행·DB 적재·curl 요청처럼 내 컴퓨터에서 명령을 실행하기 전에는 무엇을 할지 한 줄로 알리고 진행한다.

### 0-3. 확인 순서
각 항목마다:
1. **코드 확인** — 관련 Controller / Service / Repository / Entity / 템플릿 / SecurityConfig를 찾아 기대 결과를 만드는 로직(검사·분기·권한·트랜잭션)이 있는지 본다.
2. **실행 확인** (가능하면) — 앱을 띄우고 요청을 보내 응답·리다이렉트·DB 값을 확인한다.
   - DB 다시 적재:
     ```bash
     mysql -u root -p -e "DROP DATABASE IF EXISTS nolibang; CREATE DATABASE nolibang DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci"
     mysql -u root -p --default-character-set=utf8mb4 nolibang < src/main/resources/sql/schema.sql
     mysql -u root -p --default-character-set=utf8mb4 nolibang < src/main/resources/sql/seed.sql
     ```
     (비밀번호는 `application.yaml`의 DB 설정을 따른다. 모르면 사용자에게 묻는다.)
   - 앱 실행: `./gradlew bootRun` (Windows 기본 터미널이면 `gradlew.bat bootRun`), 백그라운드로 띄우고 끝나면 종료한다.
   - 로그인 요청: SecurityConfig에서 로그인 URL·아이디/비밀번호 파라미터 이름을 확인 → `GET` 로그인 화면에서 `_csrf` 값 추출 → 쿠키 저장(`-c/-b cookies.txt`)하며 `POST`. POST 요청마다 `_csrf`를 함께 보낸다.
   - 계정마다 쿠키 파일을 따로 쓴다(`learner.txt`, `teacherA.txt` …).
3. 브라우저가 꼭 필요한 항목(영상 실제 재생, 파일 선택 UI, 화면 배치 등)은 코드 + 요청으로 확인할 수 있는 데까지 하고 **"수동 확인 필요"**로 표시한다.

4. **다른 파트 기능이 앞 단계로 필요한 경우** — 이 파일은 다른 파트 검증 결과를 기다리지 않는다. 앞 단계(예: 승인, 차시 완료, 수강 확정)는 먼저 앱 기능으로 만들어 보고, 그 기능이 실패하거나 시간이 오래 걸리면 **DB에 직접 그 상태를 만든 뒤** 내 항목을 계속 확인한다. 이때 근거 칸에 "앞 단계 DB로 준비" + 사용한 SQL을 적고, 앞 단계 기능의 문제는 "다른 파트 참고"에 적는다. 앞 단계 실패를 내 항목의 ❌로 판정하지 않는다.

### 0-4. 판정 기호
| 기호 | 뜻 |
|---|---|
| ✅ | 실행해서 기대 결과 확인 |
| ✅🔍 | 실행은 못 했지만 코드상 기대 결과대로 구현됨 |
| ❌ | 기대 결과와 다름 / 구현 안 됨 |
| ⚠️ | 일부만 맞음 |
| ❓ | 기획이 정하지 않아 판단 불가 |
| 🖐 | 수동(브라우저) 확인 필요 |

### 0-5. 결과 파일
`검증결과_파트1.md`를 이 파일과 같은 폴더에 만든다.

```markdown
# 검증 결과 — 파트 1/4 (검증일)

## 요약
| 판정 | 개수 |
| ✅ | n | ✅🔍 | n | ❌ | n | ⚠️ | n | ❓ | n | 🖐 | n |

## ❌·⚠️ 목록 (먼저 볼 것)
| ID | 증상 | 원인 추정 (파일:줄) | 고칠 위치 제안 |

## 항목별 결과
| ID | 판정 | 근거 (파일:줄 / 요청→응답 / SQL 결과) | 비고 |
```

- 근거는 짧게, 하지만 다른 사람이 다시 확인할 수 있게 적는다.
- 고칠 방법은 **제안만** 적고 코드는 바꾸지 않는다.
- 다른 파트 영역의 문제를 발견하면 결과 파일 맨 아래 "다른 파트 참고"에 적는다.

## 3. ❓ 이 파트에서 판단이 필요한 것

- 인증 메일이 실제로 발송되는지, 개발용으로 로그에 링크만 찍는지 (AU-06, AU-16).
- 시드에 **준비 중** 취미가 있는지. 없으면 EX-03은 DB 상태를 바꿔서 확인.
- 권한 없는 취미 분반에 강사를 지정할 때 거부하는지 (AD-06).
- FR-005의 유휴 1시간 만료·영상 재생 중 로그인 유지는 시간이 걸려 시연 방법 정해야 함 (`session.timeout`을 잠시 줄여 확인하는 방법 등).

> 위 항목은 기획이 정하지 않았다. 구현이 어떻게 되어 있는지만 적고 판정은 ❓로 둔다.
